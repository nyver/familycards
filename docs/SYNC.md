# Протокол синхронизации

Этот документ описывает реализованный в `server/internal/sync` протокол дельта-синхронизации. Клиентская реализация (Flutter) должна следовать тем же правилам — в первую очередь правилу LWW ниже — иначе два офлайн-устройства не сойдутся к одинаковому состоянию.

## Модель

- Единица синхронизации — элемент (`item`) целиком: карта или запись настроек. Дробления на поля нет.
- Каждый сейф (`vault`) имеет монотонный счётчик `last_rev`. Каждая принятая запись получает `rev = last_rev + 1` в той же транзакции, что и сам инкремент — ревизии строго возрастают, без дыр и без повторов.
- Сервер не читает содержимое элемента: `nonce` и `ciphertext` — непрозрачные байты.

## Правило LWW (last-writer-wins)

Реализовано в `server/internal/sync/resolve.go` как чистая функция `Resolve`, независимая от ввода-вывода. Полный набор тестовых векторов, которые обязаны совпадать на сервере и на клиенте, лежит в [`testdata/lww_vectors.json`](../testdata/lww_vectors.json) в корне репозитория.

Правило:

```
если текущей записи на сервере нет:
    принять тогда и только тогда, когда base_rev == 0
иначе если current.rev == base_rev:
    принять (клиент видел актуальное состояние)
иначе:
    принять тогда и только тогда, когда (updated_at, device_id) входящей записи
    лексикографически строго больше (current.updated_at, current.device_id):
      — сначала сравниваются updated_at,
      — при равенстве — device_id как тайбрейк
```

Удаление (`deleted = true`, tombstone) участвует в этом сравнении наравне с обычной правкой — отдельного правила для удаления нет.

## `GET /v1/sync/changes`

- Параметры: `since` (последняя известная клиенту ревизия), `limit` (по умолчанию 200, не более 500).
- Возвращает элементы с `rev > since`, отсортированные по возрастанию `rev`.
- `next_since` — ревизия последнего элемента в выдаче (или `since`, если выдача пуста).
- `has_more = next_since < server_rev` — поскольку ревизии присваиваются без дыр, это условие точно отражает наличие ещё не полученных элементов.
- Клиент обязан сохранять `next_since` после применения **каждой** страницы, а не только в конце цикла — так прерывание синхронизации не приводит к повторной обработке уже применённых страниц.

## `POST /v1/sync/push`

- Тело содержит `device_id` (обязан совпадать с устройством, которому принадлежит access-токен) и до 100 элементов.
- Весь батч обрабатывается в одной транзакции `BEGIN IMMEDIATE` на пуле из одного соединения-писателя (`writeDB.SetMaxOpenConns(1)`), поэтому конкурентные пуши сериализуются самим пулом `database/sql`, а не гонкой за блокировку файла — это то, что устраняет `SQLITE_BUSY` под нагрузкой.
- Перед обработкой элементов сервер декодирует и валидирует **все** элементы батча (base64, обязательность `nonce`/`ciphertext` для неудалённых записей, разбор JSON). Ошибка в любом из них отклоняет весь запрос целиком — ничего не записывается, `last_rev` не меняется. Это делает атомарность батча более строгой, чем просто «транзакция БД»: даже если бы транзакция и не потребовалась, некорректный элемент №5 из 10 не даёт записаться ни одному из десяти.
- Все `blob_refs`, упомянутые где-либо в батче, обязаны существовать в таблице `blobs` этого сейфа **до** пуша. Если хотя бы одного не хватает — весь батч отклоняется кодом 409, ничего не сохраняется.
- Для каждого элемента вызывается `Resolve`. При принятии — инкремент `last_rev`, `UPSERT` строки элемента, пометка `blob_refs` как `referenced = 1`. При конфликте элемент добавляется в `conflicts` с полной текущей серверной версией; **транзакция не откатывается** — конфликт является штатным исходом протокола, а не ошибкой.
- Особый случай: если `base_rev != 0`, а текущей записи на сервере нет вовсе (например, физически вычищенный tombstone), сервер сообщает об этом клиенту как о конфликте с синтетической записью `{deleted: true, rev: 0}` — так клиент сходится к состоянию «элемента больше нет», вместо того чтобы воскресить его как новый.

## Жизненный цикл tombstone

Удаление — обычная запись с `deleted = true`, `nonce = NULL`, `ciphertext = NULL`. Она хранится `WALLET_TOMBSTONE_DAYS` (по умолчанию 90) дней, после чего фоновая задача (`cleanupTombstones` в `cmd/wallet/main.go`, раз в 24 часа) физически удаляет строку из таблицы `items`.

## Жизненный цикл блоба

1. Клиент загружает блоб через `POST /v1/blobs` **до** пуша элемента, который на него ссылается.
2. До первого подтверждающего пуша блоб находится в состоянии `referenced = 0`.
3. Успешный пуш элемента с этим `blob_id` в `blob_refs` помечает блоб `referenced = 1` — в той же транзакции, что и сохранение элемента.
4. Сборка мусора (`internal/blobs.RunGC`, раз в 24 часа):
   - удаляет блобы с `referenced = 0` старше 24 часов (загружены, но так и не подтверждены пушем);
   - удаляет блобы с `referenced = 1`, на которые не ссылается ни один неудалённый элемент, если с последнего изменения прошло 7 дней.
   - Обе проверки перед физическим удалением **повторно** выполняются внутри той же транзакции, что и сам `DELETE` — это закрывает гонку, при которой блоб становится (вновь) актуальным между построением списка кандидатов на удаление и самим удалением.

## Клиентский цикл

Реализован в `mobile/lib/features/sync/sync_service.dart` (`SyncService.runOnce` — один цикл; `SyncController` — триггеры и бэкофф), по спецификации `client/sync` (`openspec/changes/add-family-card-wallet/specs/client/sync/spec.md`).

Один цикл (`SyncService.runOnce`), строго в этом порядке:

1. Загрузка ещё не отправленных локальных блобов (`POST /v1/blobs`).
2. Отправка несинхронизированных карт батчами по 100 (`POST /v1/sync/push`); конфликты применяются немедленно — серверная версия перезаписывает локальную, признак несинхронизированности снимается.
3. Постраничное получение чужих изменений (`GET /v1/sync/changes`) до `has_more = false`, с сохранением курсора (`sync_state.last_server_rev`) после каждой страницы. Для входящей записи, у которой есть локальная несинхронизированная версия, применяется та же функция `Resolve` (реализована в Dart как `ConflictResolver.accept`/`localWinsOverRemote` в `features/sync/conflict_resolver.dart`), что и на сервере — набор тестов гоняется на общих `testdata/lww_vectors.json`.
4. Ленивая фоновая догрузка недостающих фото для видимых карт (`GET /v1/blobs/{id}`) — по одному блобу, ошибка одного не прерывает цикл.
5. Обновление `sync_state.last_sync_at`.

Не более одного цикла одновременно (`_running`-флаг, установленный синхронно до первого `await`, чтобы исключить гонку между проверкой и установкой); запуск без сети завершается немедленно без единого запроса.

Триггеры (`SyncController`): старт приложения, возврат из фона, локальное изменение (дребезг ~3 с — таймер перезапускается только при *росте* числа несинхронизированных карт), «потянуть для обновления», периодически раз в 15 минут. Сбой цикла запускает экспоненциальный бэкофф (2/4/8/16/30 с, не более пяти попыток подряд) без модальных сообщений об ошибке.
